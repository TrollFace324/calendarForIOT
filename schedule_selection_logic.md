# Логика подбора индивидуального расписания

**Проект:** приложение для автоматизированного подбора индивидуальной
образовательной траектории в Modeus\
**Документ:** проектирование алгоритма и MVP\
**Версия:** 1.0

## 1. Цель и постановка задачи

Студенту необходимо выбрать учебные группы по нескольким дисциплинам. У
одной дисциплины может быть несколько доступных групп, отличающихся
преподавателями, днями и временем занятий. Ручной подбор требует
перебора комбинаций, проверки пересечений, оценки окон и сравнения
преподавателей. Кроме того, студенту нужны запасные варианты на случай,
если выбранная группа станет недоступна.

Приложение должно: 1. Получить список дисциплин и доступных групп. 2.
Сформировать возможные комбинации групп. 3. Исключить комбинации,
нарушающие обязательные ограничения. 4. Оценить оставшиеся расписания по
предпочтениям студента. 5. Отсортировать варианты по заданному порядку
приоритетов. 6. Показать несколько лучших расписаний и различия между
ними. 7. Помочь быстро пересчитать варианты, если группа стала
недоступна.

Главное различие: - **Допустимость** --- расписание можно использовать:
нет запрещённых конфликтов и выполнены обязательные условия. -
**Качество** --- насколько допустимое расписание соответствует
предпочтениям студента.

Сначала нужно найти допустимые расписания, затем ранжировать их по
качеству.

## 2. Входные данные и внутренняя модель

Алгоритм не должен зависеть от конкретного формата выгрузки Modeus.
Формат данных пока необходимо подтвердить на реальном примере. Между
источником и алгоритмом нужен адаптер импорта:

``` text
Выгрузка Modeus
      |
      v
Адаптер импорта
      |
      v
Нормализация
      |
      v
Внутренняя модель
      |
      v
Алгоритм подбора
```

Если формат выгрузки изменится, потребуется обновить адаптер, а не сам
алгоритм.

### 2.1. Основные сущности

  -----------------------------------------------------------------------
  Сущность                Назначение              Пример полей
  ----------------------- ----------------------- -----------------------
  Дисциплина              Предмет, по которому    `id`, `name`,
                          нужно выбрать группу    `is_required`

  Группа                  Вариант прохождения     `id`, `course_id`,
                          дисциплины              `teacher_ids`,
                                                  `availability`

  Преподаватель           Преподаватель группы    `id`, `name`
                          или отдельного занятия  

  Занятие                 Конкретная пара или     `id`, `group_id`,
                          повторяющееся событие   `start`, `end`,
                                                  `weekday`, `weeks`

  Предпочтение            Отношение студента к    `target_id`, `level`,
                          преподавателю или       `course_id`
                          условию                 

  Настройки               Порядок критериев и     `priority_order`,
                          параметры оценки        `window_threshold`
  -----------------------------------------------------------------------

Одна группа может содержать несколько занятий в неделю, например лекцию
и практику в разные дни. Поэтому расписание группы --- это набор
занятий, а не один временной интервал.

Для занятия желательно хранить: - дату или день недели; - время начала и
окончания; - дисциплину и группу; - преподавателя или преподавателей; -
периодичность; - чётность/нечётность недели, если это применимо; -
статус доступности, если он есть в исходных данных.

### 2.2. Особенность повторяющихся занятий

Сравнения только по дню недели и времени недостаточно. Например, две
пары могут проходить в одно время, но одна --- по чётным неделям, а
другая --- по нечётным. Фактического конфликта между ними нет.

Надёжный подход --- развернуть шаблон расписания в реальные даты
семестра и сравнивать занятия по датам. Если это нецелесообразно, можно
отдельно анализировать шаблоны чётной и нечётной недель.

## 3. Жёсткие ограничения и мягкие предпочтения

Это фундаментальное разделение. Не следует объединять все условия в одну
сумму баллов.

### 3.1. Жёсткие ограничения (Hard Constraints)

Нарушение любого такого условия делает расписание недопустимым.

Для MVP: 1. По каждой обязательной дисциплине выбирается ровно одна
группа. 2. Нельзя выбрать группу, недоступную для записи. 3. Занятия не
должны пересекаться по времени в одну и ту же дату. 4. Все обязательные
дисциплины должны быть представлены. 5. Группы, явно запрещённые
пользователем, не рассматриваются.

Проверка пересечения интервалов `[start1, end1)` и `[start2, end2)`:

``` text
start1 < end2 AND start2 < end1
```

Например, 09:00--10:30 и 10:00--11:30 пересекаются. Если первое занятие
заканчивается ровно в 10:30, а второе начинается в 10:30, пересечения
нет.

Жёсткое ограничение нельзя компенсировать хорошим преподавателем или
отсутствием субботы.

### 3.2. Мягкие предпочтения (Soft Constraints)

Это пожелания, влияющие на рейтинг, но не делающие расписание
автоматически недопустимым: - предпочтительные преподаватели; -
нежелательные преподаватели; - отсутствие занятий по субботам; -
минимальное количество окон; - минимальное количество учебных дней; -
предпочтительное время начала и окончания занятий.

Алгоритм сначала фильтрует варианты по жёстким ограничениям, а затем
оценивает оставшиеся по мягким.

## 4. Предпочтения по преподавателям

Предлагается следующая шкала:

  Уровень        Значение                                         Базовый балл
  -------------- -------------------------------------------- ----------------
  Очень хочу     Максимально предпочтительный преподаватель                 +3
  Желательно     Хотелось бы попасть к преподавателю                        +1
  Без разницы    Нейтральное отношение                                       0
  Нежелательно   Предпочёл бы другого преподавателя                         -2
  Исключить      Не хочу выбирать этого преподавателя           Жёсткий запрет

Баллы --- стартовые значения для MVP. Их можно изменить после
тестирования.

Важно различать «нежелательно» и «исключить»: - **Нежелательно** ---
группа остаётся допустимой, но получает отрицательный вклад в рейтинг. -
**Исключить** --- группа не рассматривается вообще, если в ней есть
запрещённый преподаватель.

Предпочтения лучше хранить с привязкой к дисциплине. Один и тот же
преподаватель может быть желателен на одном предмете и нежелателен на
другом.

Если у группы несколько преподавателей, правило объединения предпочтений
нужно определить отдельно. В базовой модели каждый преподаватель
учитывается один раз в рамках связки «дисциплина --- группа ---
преподаватель», а не по числу проводимых им пар. Иначе преподаватель,
ведущий больше занятий, получит искусственно больший вес.

### 4.1. Расчёт оценки преподавателей

Для MVP можно использовать сумму баллов:

``` text
teacher_score = сумма баллов предпочтений
                по выбранным группам
```

Пример:

  Дисциплина         Преподаватель       Балл
  ------------------ --------------- --------
  Математика         Иванов                +3
  Программирование   Петров                +1
  Базы данных        Сидоров               -2
  **Итого**                            **+2**

Чем выше `teacher_score`, тем лучше вариант по критерию преподавателей.

У суммирования есть особенность: несколько преподавателей с уровнем
«Желательно» могут в сумме обойти одного преподавателя с уровнем «Очень
хочу». Это приемлемо, если предпочтения рассматриваются как суммарная
полезность.

Если «Очень хочу» должно быть безусловно важнее любого количества
«Желательно», вместо суммы следует сравнивать вектор:

``` text
(
    количество_очень_желательных,
    количество_желательных,
    -количество_нежелательных
)
```

Тогда сначала сравнивается число преподавателей высшего уровня, затем
следующего уровня и так далее.

**Рекомендация для MVP:** начать с суммы `+3 / +1 / 0 / -2`, а запреты
хранить отдельно. В будущем можно добавить режим строгого сравнения
категорий.

## 5. Как сортировать приоритеты

Это центральное решение алгоритма. Недостаточно присвоить критериям
баллы: нужно определить, может ли нижестоящий критерий компенсировать
проигрыш по вышестоящему.

Допустим, студент установил: 1. Очень хочу попасть к конкретному
преподавателю. 2. Не хочу учиться по субботам. 3. Хочу минимизировать
окна.

Если желанный преподаватель ведёт занятие в субботу, что важнее ---
преподаватель или свободная суббота? Ответ должен определяться
настройкой порядка приоритетов.

### 5.1. Вариант A --- взвешенная сумма

Каждому критерию задаётся вес:

``` text
total_score =
    teacher_score * teacher_weight
    + saturday_score * saturday_weight
    + windows_score * windows_weight
```

Например:

  Критерий          Вес
  --------------- -----
  Преподаватели     100
  Суббота            50
  Окна               20

Плюсы: - просто реализовать; - легко объяснить; - можно гибко
настраивать веса.

Минус: нижестоящие критерии могут компенсировать проигрыш по
вышестоящему. Даже высокий вес не гарантирует абсолютного приоритета,
если диапазоны оценок заранее не ограничены.

Поэтому обычная взвешенная сумма не всегда соответствует формулировке
«преподаватель важнее субботы при любых обстоятельствах».

### 5.2. Вариант B --- лексикографическая оптимизация

Критерии сравниваются строго по очереди.

Например: 1. Преподаватели. 2. Суббота. 3. Окна. 4. Количество учебных
дней. 5. Удобство времени.

Алгоритм сравнивает два расписания по первому критерию. Если оценки
отличаются, победитель определён. К следующему критерию он переходит
только при равенстве предыдущего.

Пример:

  Критерий                Расписание А   Расписание Б
  --------------------- -------------- --------------
  Балл преподавателей               +3              0
  Субботы                            1              0
  Окна                           0 мин          0 мин
  Учебные дни                        4              4

Побеждает А: преподаватель стоит выше субботы, поэтому отсутствие
субботы не может компенсировать проигрыш по преподавателю.

Именно этот подход соответствует исходному примеру с желанным
преподавателем в субботу.

### 5.3. Рекомендуемый вариант --- гибридная модель

Для проекта рекомендуется: - жёсткие ограничения проверять отдельно; -
критерии пользователя сравнивать лексикографически; - внутри отдельного
критерия разрешить использовать сумму баллов или несколько метрик.

Пример структуры:

``` text
1. Преподаватели:
   суммарный балл предпочтений — максимизировать.

2. Суббота:
   число суббот с занятиями — минимизировать;
   при равенстве число субботних пар — минимизировать.

3. Окна:
   суммарная длительность — минимизировать;
   при равенстве количество окон — минимизировать;
   затем максимальную длительность окна — минимизировать.

4. Учебные дни:
   число дней с занятиями — минимизировать.

5. Время:
   штраф за отклонение от предпочтительного времени — минимизировать.
```

Так студент может менять порядок критериев, а алгоритм при этом остаётся
предсказуемым.

### 5.4. Реализация сортировки

Порядок критериев хранится в настройках, например:

``` python
priority_order = [
    "teacher_score",
    "saturday_days",
    "saturday_classes",
    "window_minutes",
    "window_count",
    "max_window",
    "study_days",
    "time_penalty",
]
```

Для каждого расписания рассчитываются метрики. В простом случае ключ
сортировки выглядит так:

``` python
def ranking_key(schedule):
    return (
        -schedule.teacher_score,
        schedule.saturday_days,
        schedule.saturday_classes,
        schedule.window_minutes,
        schedule.window_count,
        schedule.max_window,
        schedule.study_days,
        schedule.time_penalty,
    )
```

Python сортирует по возрастанию, поэтому у максимизируемого
`teacher_score` стоит минус. Остальные показатели минимизируются.

В рабочем варианте ключ нужно формировать динамически на основании
`priority_order`, чтобы пользователь мог менять последовательность
критериев.

``` python
sorted_schedules = sorted(
    schedules,
    key=ranking_key
)
```

Если все критерии совпали, расписания равноценны. Для стабильного
отображения можно использовать технический дополнительный ключ ---
например, идентификаторы групп. Нельзя выдавать такой технический
порядок за реальное преимущество.

## 6. Как рассчитывать критерии

### 6.1. Суббота

Предлагается учитывать: 1. Количество суббот, в которые есть занятия. 2.
При равенстве --- количество субботних пар.

Это означает, что один занятый субботний день предпочтительнее двух
занятых суббот, даже если во втором случае суммарно меньше пар.

По умолчанию суббота --- мягкий критерий. Если пользователь хочет
полностью запретить занятия в субботу, это можно переключить в жёсткое
ограничение.

При чередовании недель нужно считать реальные субботы семестра или
нормализованные шаблоны недель.

### 6.2. Окна

Окно --- свободный промежуток между двумя занятиями в пределах одного
учебного дня.

Пример:

``` text
09:00–10:30  Математика
10:30–12:00  Программирование
15:00–16:30  Базы данных
```

Между первой и второй парой окна нет. Между второй и третьей --- 180
минут.

**Не учитывается время до первой пары и после последней пары дня.**

Предлагаемые метрики: - `window_minutes` --- сумма длительности всех
окон; - `window_count` --- количество окон; - `max_window` --- самое
длинное окно.

Пример:

  День          Занятия                                             Окна
  ------------- ------------------------------------------ -------------
  Понедельник   09:00--10:30, 12:00--13:30, 16:00--17:30         150 мин
  Вторник       10:00--11:30, 12:00--13:30                         0 мин
  Среда         09:00--10:30, 14:00--15:30                       210 мин
  **Итого**                                                  **360 мин**

Можно ввести порог: например, перерыв 15 минут не считать полноценным
окном. Порог должен быть настраиваемым, поскольку для разных студентов
короткий перерыв может иметь разное значение.

Расчёт для каждого дня: 1. Отсортировать занятия по времени начала. 2.
Взять окончание предыдущего занятия. 3. Вычесть его из начала
следующего. 4. Если промежуток больше заданного порога, учесть его как
окно. 5. Не учитывать время до первого и после последнего занятия.

### 6.3. Количество учебных дней

Количество дней, в которые у студента есть хотя бы одно занятие.

Например, расписание на четыре дня может быть предпочтительнее
расписания на пять дней, если более важные критерии совпадают. При
чередовании недель показатель нужно рассчитывать по фактическим неделям
семестра.

### 6.4. Удобство времени

Можно дать пользователю возможность указать: - не начинать раньше
заданного времени; - заканчивать до определённого времени; -
предпочитать утренние или дневные занятия; - избегать поздних пар.

Для MVP достаточно штрафа за отклонение от заданных границ. Этот
критерий по умолчанию должен быть ниже преподавателей, субботы и окон.

## 7. Генерация расписаний: Backtracking

Для первой версии рекомендуется использовать **Backtracking (поиск с
возвратом)**.

Идея: последовательно выбрать по одной группе для каждой дисциплины.
После каждого выбора проверять, можно ли добавить эту группу к уже
сформированному расписанию. Если возник конфликт, вернуться к
предыдущему выбору и попробовать другую группу.

### 7.1. Пример входных данных

  Дисциплина         Группа   Преподаватель   Время
  ------------------ -------- --------------- -----------------
  Математика         M1       Иванов          Пн 09:00--10:30
  Математика         M2       Петров          Сб 10:00--11:30
  Программирование   P1       Сидоров         Пн 10:00--11:30
  Программирование   P2       Козлов          Вт 12:00--13:30
  Базы данных        D1       Орлов           Вт 12:30--14:00
  Базы данных        D2       Смирнов         Чт 09:00--10:30

Всего комбинаций: `2 * 2 * 2 = 8`.

Но: - M1 + P1 конфликтуют в понедельник с 10:00 до 10:30; - P2 + D1
конфликтуют во вторник с 12:30 до 13:30.

Эти ветки поиска можно отбросить сразу, не формируя полное расписание.

### 7.2. Псевдокод

``` python
def search(index, selected_groups):
    if index == len(courses):
        schedule = build_schedule(selected_groups)
        metrics = calculate_metrics(schedule)
        save_if_top_n(schedule, metrics)
        return

    course = courses[index]

    for group in course.groups:
        if not is_available(group):
            continue

        if violates_hard_constraints(group, selected_groups):
            continue

        selected_groups.append(group)
        search(index + 1, selected_groups)
        selected_groups.pop()
```

Это базовая схема. В реальной реализации нужно добавить фильтрацию
запретов преподавателей, учёт дат и недель, ограничение TOP-N и
дедупликацию.

### 7.3. Ускорение поиска

**MRV (Minimum Remaining Values).** Сначала обрабатывать дисциплины с
наименьшим числом доступных групп. Если у одной дисциплины две группы, а
у другой десять, выгоднее начать с первой: она быстрее ограничит
пространство поиска.

**Ранняя проверка конфликтов.** Проверять совместимость сразу после
добавления группы, не дожидаясь полного расписания.

**TOP-N.** Если нужны только 10 лучших вариантов, не хранить все
допустимые комбинации. Поддерживать ограниченный набор лучших
результатов.

**Дедупликация.** Не показывать одинаковые наборы групп несколько раз.

**Branch and Bound.** В дальнейшем можно оценивать максимально возможное
качество незавершённой ветки. Если даже оптимистичная оценка не сможет
превзойти худший результат в TOP-N, ветку можно прекратить. Для MVP это
необязательно.

В худшем случае Backtracking экспоненциальный. Например, 10 дисциплин по
5 групп дают `5^10 = 9 765 625` комбинаций до отсеивания. Ранняя
проверка конфликтов может сильно сократить перебор, но
производительность нужно измерить на реальных данных.

## 8. Запасные варианты

Запасные варианты должны помогать студенту быстро перестроить
расписание, если выбранная группа стала недоступна.

### 8.1. Основной сценарий

1.  Сгенерировать TOP-N расписаний.
2.  Сохранить набор групп каждого варианта.
3.  Если группа стала недоступна, исключить её из входных данных.
4.  Повторно запустить алгоритм.
5.  Показать новые лучшие варианты.

Это надёжнее, чем пытаться заранее предусмотреть все изменения
доступности.

### 8.2. Альтернативы с заменой одной группы

Можно дополнительно найти варианты, отличающиеся от основного только
одной группой:

``` text
Основное:
Математика: M1
Программирование: P1
Базы данных: D1

Запасное:
Математика: M1
Программирование: P2
Базы данных: D1
```

Пользователь сразу видит, какую группу можно заменить.

### 8.3. Разнообразие вариантов

TOP-N может содержать много почти одинаковых расписаний. Поэтому
полезно: - удалять дубликаты; - показывать отличия от основного
варианта; - при равном качестве отдавать предпочтение вариантам, которые
дают альтернативы по разным дисциплинам.

Нужно различать альтернативное расписание и подтверждённое место в
группе. Приложение может предложить запасной вариант, но не должно
обещать, что место в нём сохранится. Если источник предоставляет статус
доступности, его следует обновлять перед использованием результата.

## 10. Когда понадобится Google OR-Tools CP-SAT

Backtracking подходит для MVP, но при большом числе дисциплин и сложных
зависимостях поиск может стать дорогим.

**CP-SAT** --- решатель задач удовлетворения ограничений и оптимизации.
Разработчик описывает переменные, запрещённые комбинации и целевую
функцию, а решатель ищет подходящее решение.

Его стоит рассмотреть, если: - число дисциплин и групп существенно
выросло; - появились сложные зависимости между выбором групп; - возникли
ограничения по нагрузке, преподавателям, аудиториям и другим ресурсам; -
Backtracking не укладывается в приемлемое время; - требуется более
серьёзная оптимизация.

**Рекомендация:** не начинать с CP-SAT. Сначала реализовать модель
данных и Backtracking, проверить корректность на реальных данных и
измерить производительность. При необходимости заменить механизм поиска,
сохранив интерфейсы моделей, ограничений и оценки.

## 11. Обработка реальных данных

Перед запуском алгоритма необходимо проверять: - группы без
дисциплины; - занятия без времени начала или окончания; - окончание
раньше начала; - неизвестных преподавателей; - дублирующиеся занятия; -
неполные расписания; - некорректные даты; - отсутствующую информацию о
доступности.

Ошибочные записи нельзя молча считать корректными. Их нужно показать в
отчёте импорта.

### 11.1. Чётные и нечётные недели

Два занятия в один день и время не конфликтуют, если одно проходит
только по чётным неделям, а другое --- только по нечётным. Желательно
развернуть расписание в реальные даты семестра и сравнивать фактические
интервалы.

### 11.2. Часовые пояса

Время из выгрузки нужно интерпретировать в часовом поясе учебного
заведения, а не компьютера пользователя. Внутренняя модель должна
сохранять однозначное представление даты и времени.

### 11.3. Границы семестра

Повторяющиеся занятия учитываются только в пределах семестра. Если
источник предоставляет сведения об отменах и переносах, их нужно
учитывать при построении фактического расписания.

## 12. Пример сравнения вариантов

Пользователь установил порядок: 1. Преподаватели. 2. Суббота. 3. Окна.
4. Учебные дни.

Алгоритм сформировал три допустимых варианта:

  Показатель              Вариант A   Вариант B   Вариант C
  --------------------- ----------- ----------- -----------
  Балл преподавателей            +5          +3          +5
  Занятые субботы                 1           0           0
  Окна                       60 мин       0 мин     120 мин
  Учебные дни                     4           4           3

Сравнение: 1. A и C имеют одинаковый балл преподавателей. 2. У C меньше
занятых суббот, поэтому C лучше A. 3. B имеет меньший балл
преподавателей, поэтому проигрывает C и A, несмотря на отсутствие суббот
и окон. 4. Между A и B первым сравниваемым критерием остаются
преподаватели: A получает +5, B --- +3, поэтому A выше B.

Итог:

``` text
1. Вариант C
2. Вариант A
3. Вариант B
```

Это показывает, почему нельзя бездумно складывать все показатели:
лексикографическая сортировка сохраняет заданную иерархию.

## 14. План реализации MVP

### Этап 1. Подготовка модели данных

-   Получить пример выгрузки Modeus.
-   Определить реальные поля и структуру.
-   Разработать модели дисциплин, групп и занятий.
-   Написать адаптер импорта и нормализацию.
-   Проверить качество данных.

**Результат:** алгоритм получает единый внутренний формат, не зависящий
от исходной выгрузки.

### Этап 2. Жёсткие ограничения

-   Выбор одной группы на дисциплину.
-   Проверка пересечений.
-   Проверка доступности групп.
-   Учёт недель и дат.
-   Автоматические тесты.

**Результат:** алгоритм строит только допустимые расписания.

### Этап 3. Оценка и сортировка

-   Предпочтения преподавателей.
-   Подсчёт суббот.
-   Подсчёт окон.
-   Количество учебных дней.
-   Пользовательский порядок критериев.
-   Лексикографическая сортировка.

**Результат:** допустимые расписания ранжируются по предпочтениям
студента.

### Этап 4. Генерация TOP-N

-   Backtracking.
-   Ранняя проверка конфликтов.
-   Эвристика MRV.
-   Ограничение числа сохраняемых вариантов.
-   Дедупликация.

**Результат:** пользователь получает несколько лучших расписаний.

### Этап 5. Запасные варианты

-   Исключение ставшей недоступной группы.
-   Повторный поиск.
-   Поиск замен одной группы.
-   Отображение различий между вариантами.

**Результат:** студент может быстро перестроить расписание.

### Этап 6. Производительность

-   Измерение времени на реальных данных.
-   Нагрузочные сценарии.
-   Оценка числа комбинаций.
-   Решение о необходимости CP-SAT.

**Результат:** понятны ограничения текущего алгоритма и необходимость
дальнейшей оптимизации.

## 16. Что уточнить после получения выгрузки

1.  Какие сущности реально присутствуют: дисциплины, группы, потоки,
    преподаватели, отдельные занятия?
2.  Есть ли чётность недель, даты начала и окончания, отмены и переносы?
3.  Можно ли определить актуальную доступность группы и число свободных
    мест?
4.  Всегда ли студент выбирает ровно одну группу на дисциплину?
5.  Бывают ли дисциплины, для которых отдельно выбираются лекция и
    практика?
6.  Может ли одна группа включать занятия с несколькими преподавателями?
7.  Как в выгрузке обозначены время и часовой пояс?

Ответы могут повлиять на модель данных, но не меняют основной принцип
алгоритма:

**Жёсткие ограничения → генерация допустимых расписаний → расчёт метрик
→ сортировка по пользовательским приоритетам → запасные варианты.**

Приоритеты должны быть предсказуемыми. Если преподаватель стоит выше
субботы, никакое количество преимуществ по субботам и окнам не должно
позволить варианту с менее предпочтительным преподавателем обойти
вариант с более предпочтительным преподавателем.
